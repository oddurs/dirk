## Problem

Screenshots of a terminal are the worst of both worlds: a PNG that cannot be
selected, cannot be searched, goes blurry on a retina display, weighs two
hundred kilobytes, and is out of date the moment the chrome changes.

The README already solves this for itself with hand-drawn ASCII, which is
honest but is a drawing rather than the thing.

## Proposal

`examples/shot.rs` already spawns the real binary on a real pseudo-terminal and
parses what it paints with the same `vt100` the panes use. It prints plain
text. Given `--html` it walks the cells instead and emits spans carrying the
real colours, which is a terminal render that is text: selectable, searchable,
a few kilobytes, and correct by construction.

The renders are committed under `site/shots` and regenerated by `make shots`,
not built on demand. Two reasons. A site build that has to allocate a
pseudo-terminal fails in places a site build should not fail; and a shot that
changes should show up in a diff and be looked at, which is exactly the habit
`make shot` already is.

## Acceptance criteria

- [x] `cargo run --example shot -- --html` emits a coloured terminal render
- [x] `make shots` regenerates every render under `site/shots`
- [x] The renders are text: selectable, and legible with styles disabled
- [x] The site builds with no pseudo-terminal available
